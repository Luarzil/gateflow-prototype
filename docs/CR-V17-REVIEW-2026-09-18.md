# CR-V17 review after step 4 — 2026-09-18

The owner asked for a heavy, detailed look for bugs before going further, so problems would not be
found late. This records what was checked, what was found, how each finding was proven, what was
fixed, and what is left for a decision.

## Method

Every suspect was demonstrated before it was called a bug: against the live dev service, the real
database, two real browser tabs, or simulated rows inside the database. Nothing below is inferred
from reading alone unless it says so.

The most important fixes were then **mutation-checked**: each fix was removed on purpose and the
suite run, to prove the tests actually fail without it. That check caught one test that could not
fail (below).

## Fixed

### High

1. **A full phone silently stopped saving.** Each movement costs about 1,300 characters with its
   audit entries, and the app kept every one forever. A phone's web storage holds a few megabytes,
   so a gate doing 300 movements a day filled it in roughly one to four weeks. `saveState` then
   switched saving off for the session, and the next notice still said "saved". Movements recorded
   after that existed only in memory, queued ones included.
   *Fix:* the device trims movements the shared database has confirmed, older than 14 days, with
   their own audit entries - never anything unsent, refused, or recorded before movements went to
   the cloud. If a save still fails it trims to one day and retries; if that fails, a red notice says
   the movements are **not** stored and no later notice may say "saved". Saving is retried on every
   change instead of being switched off.
   *Proven:* storage made to refuse writes - both movements showed the red notice, neither claimed
   "saved"; with storage back, the next save wrote both and the warning cleared. Old records of each
   kind were planted - only the confirmed one and its own audit entry were trimmed.

2. **Two console tabs erased each other's unsent movements.** Each tab saved its whole copy, so the
   last to save removed what the other had recorded. Demonstrated: tab A queued a movement offline,
   tab B saved, and the movement was gone from storage; closing tab A would have lost it for good.
   *Fix:* every save first takes in what another tab saved (movements and audit entries are only
   ever added, so the union loses nothing), and tabs take in each other's saves as they happen. A
   movement another tab already sent is not sent again. Resetting the demo starts a new epoch so an
   old tab cannot merge the old records back.
   *Proven:* the same experiment again - the movement survived tab B's save, and tab B knew tab A had
   since sent it.

3. **Offline movements were judged at upload time, not gate time.** The server checked whether the
   driver was authorized *now*. With the offline queue, a movement recorded yesterday while
   authorized and uploaded today after the authorization ran out was flagged as unauthorized.
   *Fix:* the authorization (including one revoked later), the license and the roster are all
   checked as of the movement's own time.
   *Proven live:* E1001 is authorized now; a movement stamped two hours before that authorization
   began was flagged `authorization_expired`. Before the fix it would have passed.

4. **Search paging could silently skip a movement.** The database keeps microseconds; the page
   cursor carried milliseconds, so a movement recorded in the same millisecond as the last row of a
   page was dropped from the next page. Proven inside the database with simulated rows (page two
   returned `8` instead of `9,8`).
   *Fix:* timestamps and cursors carry microseconds.
   *Proven live:* the whole log walked two rows at a time matched one full fetch exactly - 18 rows,
   9 pages, same order, no duplicates.

### Medium

5. **A flag blamed the driver for what the device had not shared.** Authorizations are still kept
   on the device (see gaps), so an OUT the device correctly authorized was flagged
   "authorization expired". *Fix:* the device sends the authorization it relied on; the server
   flags `authorization_not_shared` when that covers the movement. *Proven live.*
6. **The signed-in uploader was not recorded.** *Fix:* migration `004_uploaded_by` adds
   `movements.uploaded_by`, filled from the verified sign-in token and never from the request body;
   the audit entry says who uploaded. *Proven live:* the rows read `uploaded_by = raul`.
7. **A phone clock more than 10 minutes fast had every movement refused, forever.** *Fix:* a clock
   up to a day ahead is kept and flagged `device_clock_ahead`; more than a day is refused with a
   message to check the clock; a movement over 30 days old is flagged `device_clock_behind`.
   *Proven live* for 2 hours and 2 days ahead.

### Low

8. An impossible date (`2026-02-30`) and a forged page cursor both caused a 500; both are now a 400
   before any query runs. The server now insists on canonical barcodes (`g0003` is stored as
   `G0003`; `g42` is refused rather than inventing a vehicle) and letters-and-digits employee
   numbers. The search's direction column is escaped. Requests that find the token expired together
   share one refresh (mutation-checked). Signing out mid-request reports a sign-out instead of a
   crash. Escape closes the sign-in panel. All proven live or by test.

## Confirmed sound

- CORS: the Android app's origin and the review site are allowed; a stranger's site gets nothing.
- Injection: filters are parameters; a SQL-shaped search returned zero rows.
- The append-only guard refused an UPDATE on a new movement.
- Idempotency held in the worst case: a movement that arrived but whose answer was lost was resent,
  and the database still holds one row and one audit row for it.

## An incident during the review

Re-running the click-path validator after fix 2 exposed a consequence of that fix. The validator
drives the app inside its own page and rewrites the browser's storage as it goes. A signed-in tab
merged the validator's test movements into its own records, and its once-a-minute queue uploaded
**24 of them to the Veri-Gate Dev database: movements 45 to 68**, all recorded 22:56:32-22:57:35 ET
on 2026-09-18, `uploaded_by = raul`. Dev only; nothing Patrick sees.

*Fix:* inside the validator, movements get no shared-records id (so nothing can upload them), the
cloud client never starts, and every save carries a harness epoch so no open tab merges them.
*Proven:* the same conditions again - a signed-in tab open, the validator run, the queue timer
passed - and zero rows reached the database; the tab absorbed nothing.

The 24 rows remain. Movements are append-only by design, so removing them means disabling the
guard for a maintenance delete. That is the owner's decision.

## Tests that could not fail

Mutation-checking showed that the test for fix 2 still passed with the merge call deleted: it
compared positions, and a missing call reads as position -1, which is "before" everything. It now
requires the call to exist. A scan of every test found one other comparison of the same kind
(`cloud.js` loading before `app.js`), fixed the same way.

## Gaps this review found that need a decision

1. **Drivers, vehicles, authorizations, gate approvals and the location override switches are still
   kept on one computer each.** Only movements are shared. Consequences today: a driver added on
   the console is refused by the shared records; authorizations granted on the console are unknown
   to the server (now flagged truthfully, but flagged); the server cannot confirm a location's
   override switch was on. This has to move to the cloud before real use.
2. **A refused movement has no retry** once its cause is fixed (for example, the driver is later
   added to the shared roster).
3. **Printing a shared search is audited on the printing device only**, not in the shared trail.
4. **The Android app forgets its sign-in when closed** (the session lives in the tab). Device
   sign-in is step 5.
5. **Movement ids have gaps** (9-33 were skipped when Aurora resumed). Harmless, but no printout
   should present them as a sequence.
6. **Roles are not enforced by the server yet**: any signed-in login can record.
7. **No automated test drives the cloud paths end to end**; the validator and browser suites run
   signed out. The live checks in this review were done by hand.
